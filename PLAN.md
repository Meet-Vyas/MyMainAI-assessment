## Key design decisions (to justify in ARCHITECTURE.md)
- **Upload:** S3 multipart with presigned part URLs issued by the backend. The browser PUTs parts straight to MinIO/S3, so file bytes never touch the API.
  - **Part size:** 16 MiB, scaled up only if needed to stay under 10,000 parts. A 10 GB file is about 600 parts.
  - **Concurrency:** 4 parts in flight, with per-part retry and backoff.
  - **Resume:** the backend stores the `uploadId` and key in Postgres; the browser keeps a fingerprint (name, size, lastModified) mapped to the videoId in localStorage. On reload, the UI asks the user to re-select the file, the backend calls ListParts, and only the missing parts are sent.
  - **Cleanup:** cancel calls AbortMultipartUpload. A BullMQ repeatable sweeper aborts uploads with no activity for 24h. An S3 lifecycle rule (`AbortIncompleteMultipartUpload` after 2 days) is the backstop.
- **Processing:** a BullMQ `process-video` job with a long `lockDuration` that is renewed automatically, `maxStalledCount` set, 3 attempts with exponential backoff, and worker concurrency of 1 per container.
  - **Pipeline:** download the source to a temp directory, ffprobe it (reject non-video files), poster, HLS ladder, upload outputs, mark READY.
  - **Idempotency:** each run's output goes to `public/videos/{id}/hls/{uuid}/`, and the DB pointer is flipped atomically at the end. Old prefixes are cleaned up. *(Built in M5: a random id per run rather than `v{attempt}`, because a stalled re-run keeps the same attempt number.)*
  - **Resource bounds:** docker cpu/mem limits, `ffmpeg -threads`, ffmpeg run at `nice 10`, a disk check before starting, and temp directories always removed (plus wiped on start).
  - **Progress:** parsed from ffmpeg `-progress`, sent via `job.updateProgress`, and written through to the DB (throttled).
  - **Zombie recovery:** stalled jobs get re-queued, plus a reconciler that re-queues or fails UPLOADED/PROCESSING rows whose job is missing, failed or back in the queue. SIGTERM re-queues the running job without using an attempt.
- **HLS:** H.264 High profile (`yuv420p`) with AAC-LC, **MPEG-TS** segments of 6s with keyframes forced every 2 s (time-based, so variable-frame-rate phone video aligns too; no scene-cut), and VOD playlists. The ladder is the top 3 of 1080p/720p/480p/360p **at or below the source** (never upscaled), using capped CRF. One encode pass produces all renditions with `-var_stream_map` and a master playlist. This gives fast start and quick seeks. *(Settled in M5; see the decisions log.)*
- **Playback:** if `video.canPlayType('application/vnd.apple.mpegurl')`, use native playback (Safari, iOS, most webviews, and now recent desktop Chrome). Otherwise, if MSE can play H.264/AAC, use hls.js. Otherwise, show the unsupported state. *(Built in M6; see the decisions log.)*
  - Use `playsinline` and `muted`-free autoplay avoidance, plus a custom accessible control bar and a quality selector.
  - Resume position is saved per video in localStorage.
- **Storage headers:** CORS on the bucket. `.m3u8` gets `application/vnd.apple.mpegurl` with `max-age=60` (raised from the planned 10 s, since versioned prefixes mean playlists never change in place). Segments and posters get `max-age=31536000, immutable`. Set per object by the worker at upload.
- **Live status:** SSE endpoint `GET /admin/videos/events`, fed by the worker over Redis pub/sub. Polling is the fallback.

## Decisions log (copy into README / ARCHITECTURE)
- **MinIO image:** the official `minio/minio` and `minio/mc` repos are gone from Docker Hub, and quay.io needs a login. We use Bitnami's frozen archive builds `bitnamilegacy/minio:2025.7.23-debian-12-r5` and `bitnamilegacy/minio-client:2025.7.21-debian-12-r3`, pinned so reviewers run exactly what was tested. Production uses real S3, so this only affects local dev.
- **Bucket layout:** `uploads/` is private (presigned access only); `public/` allows anonymous read for HLS and posters. MinIO's default CORS already allows the frontend origin.
- **Abandoned multipart uploads (local):** MinIO's `MINIO_API_STALE_UPLOADS_EXPIRY=48h` stands in for S3's `AbortIncompleteMultipartUpload` lifecycle rule.
- **Shared `packages/db`:** the Prisma schema, migrations and client live in their own workspace (not `apps/backend`) because the worker also writes video status. Prisma 6 and jose 5 rather than the newest majors: both still ship CommonJS, which NestJS compiles to. Prisma 7 would change client generation and add driver adapters for no benefit here.
- **Auth:** scrypt (built into Node, no native add-on) with a `scrypt$N$r$p$salt$hash` format so parameters can be raised later. JWT is HS256 with issuer/audience checks, 8h expiry, in an httpOnly `SameSite=Lax` cookie (`Secure` via `COOKIE_SECURE`). An unknown email is checked against a dummy hash, so timing doesn't reveal which emails exist. The frontend proxies `/api`, so the cookie is same-origin.
- **Seed:** runs on every backend start and is idempotent. Changing `ADMIN_PASSWORD` and restarting resets the password.
- **Delete order:** abort multipart, then delete `uploads/{id}/`, then `public/videos/{id}/`, then the row. If storage fails, the row survives and the delete is retryable. Deleting while PROCESSING returns 409 until the worker can cancel jobs (milestone 5).
- **Status transitions:** defined once in `@ugn/contracts` (`canTransition`). READY is terminal; FAILED goes back to UPLOADED on retry; PROCESSING goes back to UPLOADED when the reconciler re-queues a crashed job.
- **Known audit findings (accepted):** `deepmerge-ts` via the Prisma CLI and `sprintf-js` via ts-jest. Both are DoS bugs in dev/build tooling that never handles request data. Jest was upgraded to 30 to clear the others.
- **Server-side completion:** on `/complete` the backend lists the parts S3 actually holds, checks every part number and size, and only then assembles the upload. A 409 names the missing/truncated parts so the client re-sends just those. The browser never reads `ETag`, so no CORS `ExposeHeaders` setup is needed (this resolves the earlier milestone 3 note).
- **Two S3 clients:** one for the backend's own calls (`minio:9000` in Docker) and one that only signs URLs for the host the browser uses (`S3_PUBLIC_ENDPOINT`, `localhost:9000`), because SigV4 signatures cover the host. For phone testing on a LAN, set `S3_PUBLIC_ENDPOINT=http://<LAN-IP>:9000`.
- **SDK checksum default off for presigning:** newer AWS SDKs add a CRC32 checksum to presigned UploadPart URLs, computed over an empty body, which breaks real browser uploads. Both clients use `requestChecksumCalculation: 'WHEN_REQUIRED'`.
- **Idempotent complete:** a repeat call after success returns the video. If S3 finished but the row update crashed, the next call sees `NoSuchUpload`, checks that the assembled object exists at the right size, and finishes the transition. The UPLOADING→UPLOADED update is conditional, so concurrent completes can't both win.
- **Job IDs:** `{videoId}-run{n}` (BullMQ forbids `:`). Enqueueing the same run twice is de-duplicated; an admin retry bumps `attempts` to get a new run. Job options: 3 attempts, exponential backoff from 30s, completed jobs kept 7 days and failed jobs 30 days.
- **Expired uploads:** if storage has already dropped the multipart upload (lifecycle rule), status and complete return 410 Gone and delete the video.
- **Abandoned-upload sweeper:** a BullMQ job scheduler (`maintenance` queue, every 15 min, so only one instance sweeps) deletes UPLOADING videos idle for over 24h (`ABANDONED_UPLOAD_TTL_HOURS`). Signing and status calls count as activity. 24h survives a laptop closed overnight and stays under the 48h storage-level backstop.
- **Custom thumbnail:** a presigned POST (not PUT) so storage itself enforces 5 MiB max and the exact content type. It's stored at `public/videos/{id}/custom-thumbnail` and recorded on complete. It's publicly readable as soon as it's uploaded (admin-only upload, so accepted).
- **Size limit:** 50 GiB (a 10-hour set at 8 Mbit/s is about 36 GB). The pre-upload type check is extension plus declared MIME; browsers often send `''` for `.mkv`. The real check is ffprobe in the worker.
- **Cancel** is `DELETE /admin/videos/:id`, which aborts the S3 upload and removes the objects. No separate abort endpoint.
- **Upload engine** (`apps/frontend/src/upload/UploadEngine.ts`): plain TypeScript, with the network injected, so it's unit-tested without a browser.
  - Every start or resume asks the server what's stored, so pause, page reload and a fresh start are one code path.
  - 4 parts in flight: saturates a home uplink while capping what a pause or drop throws away at 64 MiB.
  - Network errors retry forever with capped (30s), jittered backoff and a "reconnecting" state; server errors give up after 6 attempts; a 403 re-signs.
  - Links are signed 100 at a time, refreshed 5 min before expiry.
  - Stall detection: a part with no progress for 45s is aborted, because a dropped Wi-Fi link often hangs instead of erroring.
  - `File.slice()` is lazy, so a 10 GB file is never read into memory.
  - XHR, not fetch, because only XHR reports upload progress.
- **Resume after refresh:** browsers can't reopen a file by themselves, so the admin re-selects it. localStorage keeps `{videoId, name, size, lastModified, sampleHash}`, where sampleHash is SHA-256 of the first and last MiB plus the size. A different file with the same name and size is refused. WebCrypto needs a secure context, so on a plain-HTTP LAN IP the check falls back to name and size. Picking a matching file in the upload form also offers "Resume instead".
- **Live status:** SSE (`GET /api/admin/videos/events`) fed by Redis pub/sub (`video-events`), so the worker and all backend instances share it.
  - Events are small (`changed` with optional status/progress, or `deleted`); progress-only events patch in place, anything else refetches that video.
  - The client refetches the whole list on every (re)connect, so missed events don't matter, and it polls every 10s while SSE is down.
  - A 25s heartbeat keeps proxies from cutting idle streams.
  - SSE over WebSockets: one-way is enough, it's plain HTTP (cookie and proxy just work), and EventSource reconnects by itself.
- **Retry:** `POST /admin/videos/:id/retry` does a conditional FAILED→UPLOADED, increments `attempts` and enqueues run n+1, so a double-click can't queue two runs.
- **UI notes:** destructive actions use an inline two-step confirm (no `window.confirm`). Status changes are announced through an `aria-live` region. Framer Motion respects reduced motion. The left column isn't sticky, since a sticky element taller than the screen hides its bottom.
- **Vitest 5** (not 3) because Vitest 3 has critical advisories; it supports our Vite 6.4.

### Milestone 5: worker
- **Pipeline** (`apps/worker/src/processing/video-job.runner.ts`): claim → ffprobe → disk check → download → poster → one-pass HLS encode → upload → publish.
  - The runner is plain TypeScript with ffmpeg, S3 and the DB injected, so the state machine is unit-tested without them.
  - The BullMQ glue (`video.processor.ts`) only translates its result.
- **Probe before download:** ffprobe reads the source over a presigned URL with range requests, so a renamed 10 GB non-video is rejected without downloading it.
  - Known "not media" ffprobe errors throw `InvalidMediaError`, which becomes BullMQ's `UnrecoverableError`: FAILED at once, no retries.
  - Other ffprobe errors (e.g. storage unreachable) are retried.
  - Also rejected: no video stream (audio files, including cover art), images, and no duration or frame size.
- **Ladder** (`media/ladder.ts`): 1080p/720p/480p/360p with caps of 5000/3000/1500/800 kbit/s, taking the top 3 at or below the source.
  - **Never upscales.** A 720p source gets 720/480/360. Upscaling costs encode time, storage and egress for no visible gain. Assumption: the spec's "1080/720/480" describes a 1080p-or-better source.
  - Portrait is handled by fitting each rung's box in the source's orientation; rotation metadata and non-square pixels are applied first. Verified on an iPhone portrait `.mov`: 1080x1920 → 1080x1920/720x1280/480x854.
  - Anything smaller than 360p gets one variant at its own size.
- **Encode:** one ffmpeg process decodes once, `split`s, and runs 3 libx264 encoders into one HLS muxer (`-var_stream_map`, master playlist).
  - H.264 High, `yuv420p` (10-bit/4:2:2 camera files would otherwise fail on phones).
  - Capped CRF 21 with per-variant `maxrate` and 2x `bufsize`: quality-targeted, with peaks bounded for ABR. ffmpeg writes BANDWIDTH and CODECS into the master.
  - Keyframes forced every 2 s with `sc_threshold 0`, so 6 s segments align across variants.
  - AAC-LC 128k stereo 48 kHz.
  - MPEG-TS segments over fMP4, for the widest player support. fMP4 only pays off with HEVC/AV1 or DASH.
  - Preset `veryfast` (env `FFMPEG_PRESET`). A 14-minute 1080p portrait video encodes in about 10 min on 4 CPUs (~1.4x realtime).
- **Output and idempotency:** each run writes to `public/videos/{id}/hls/{random uuid}/` (master, variant folders, `poster.jpg`). One conditional UPDATE then sets READY and the new `hlsPrefix`.
  - Players never see a half-written or mixed set, and nothing is overwritten under a URL a CDN might have cached.
  - On success, sibling prefixes (crashed runs) are deleted. On any failure, the run deletes its own prefix.
  - Upload order is segments, then variant playlists, then master.
- **Ownership rule:** every worker write is `updateMany where {id, attempts: run, status in [...]}`, with the run number now in the job payload.
  - A job for a deleted video, a job superseded by an admin retry, or a duplicate delivery of a READY video just completes as "skipped".
  - Two copies of the same job racing (lock lost) can't both publish. The loser's heartbeat fails, it stops and cleans up.
- **Progress:** download is 0–5%, encode 5–90% (ffmpeg `-progress out_time_us`), upload 90–99%.
  - Written when the percentage changes, at most every 2 s, and at least every 10 s as a heartbeat. Mirrored to `job.updateProgress` and to SSE.
  - The heartbeat doubles as the **cancellation check**: once the row is gone or retried, the write matches nothing, ffmpeg is killed and the run cleans up within ~10 s.
- **Delete while processing** is now allowed. The backend deletes storage, then the row, then sweeps `public/videos/{id}/` again.
  - The second sweep closes the race where the worker uploads its last files after the first sweep and finishes just before the row goes.
  - Every worker upload happens before its final row update, so the second sweep sees them all.
- **Failure handling:**
  - Transient error with attempts left: back to UPLOADED with `failureReason` "Retrying after: …" (so the UI shows Queued, not Failed), and BullMQ retries with 30 s/60 s backoff.
  - Last attempt, or invalid media: FAILED with the reason.
  - Job options (3 attempts, backoff, retention) moved to `PROCESS_JOB_OPTIONS` in contracts, shared by the backend and the reconciler.
- **Crash recovery (BullMQ):** lock 120 s, renewed every 60 s; stalled check every 60 s; `maxStalledCount: 2`.
  - A dead worker's job is re-queued within ~3 min and doesn't use up one of the 3 attempts.
  - A job that crashes its worker 3 times fails ("stalled more than allowable limit"). The `failed` handler and the reconciler make sure the row says FAILED.
  - We started at a 60 s lock. In testing, a full-CPU encode starved Node for 54 s, the lock lapsed, and the job ran twice (harmless thanks to the ownership rule, but wasted CPU). Fix: ffmpeg runs under `nice -n 10`, and the lock is longer as margin.
- **Clean shutdown:** SIGTERM aborts the run (kills ffmpeg, deletes its partial output), sets the row back to UPLOADED, then `job.moveToWait` plus `WaitingError`. The job is re-queued at once without using an attempt.
  - Compose: `init: true` (tini) on all app containers. Node as PID 1 ignored the SIGTERM NestJS re-sends itself after its shutdown hooks, so every stop hung for the full grace period.
  - The worker also closes the Redis connections it hands to BullMQ, which doesn't close them itself.
  - `stop_grace_period: 30s`.
- **Hung ffmpeg:** killed after 60 s with no `-progress` output. Otherwise lock renewal would keep a dead encode "active" forever.
- **Reconciler** (`reconciler.service.ts`, BullMQ job scheduler every 5 min, so one instance runs it): looks at UPLOADED/PROCESSING rows not updated for 5 min (live jobs heartbeat every 10 s).
  - Job missing → re-enqueue. Job back in the queue while the row says PROCESSING → mark the row UPLOADED.
  - Job failed, or completed without moving the video on → mark FAILED with the reason.
  - Each write also requires the row to still be stale, so it can't overwrite a worker that just picked the video up.
- **Resource bounds:**
  - Compose limits of 4 CPUs and 4 GB. `FFMPEG_THREADS=4` per encoder. Measured about 650 MiB RSS for a 1080p portrait ladder.
  - Free scratch disk must cover source + estimated output (sum of caps × duration × 1.1) + 1 GiB, or the run fails as retryable.
  - Scratch is an anonymous volume per container (`/tmp/ugn`), wiped on start; a hard crash never reaches the `finally` cleanup. The old named `workertmp` volume is no longer used.
- **S3 from the worker:** one client (no browser-facing presigning), `maxAttempts: 5`, socket idle timeout 120 s.
  - Output files are uploaded as buffers (each ≤ a few MB), because the SDK can't retry a stream body.
  - Headers are set per object: `.m3u8` → `application/vnd.apple.mpegurl`, `max-age=60`; `.ts`/`.jpg` → `max-age=31536000, immutable`.
  - Playlists get 60 s rather than the planned 10 s: prefixes are versioned, so a playlist never changes in place; the TTL only bounds how long a deleted video stays on CDN edges.
- **Poster:** frame at min(10%, 30 s), at most 1280 px wide, input-seeked. A custom thumbnail, if uploaded, wins as `posterKey`.
- **Known limitations (for W2/W7):**
  - A crash restarts the encode from 0. The 10 h answer is to upload segments as they're produced and resume from the last full segment, or to transcode chunks in parallel.
  - The source is downloaded again on each retry.
  - HDR sources are converted to 8-bit without tone-mapping (colours can look washed out).
  - High frame rates aren't capped.
  - `docker kill` doesn't trigger `restart: unless-stopped` (Docker treats it as a manual stop); real crashes do.
- **Verified on the running stack:**
  - e2e (`processing.e2e-spec.ts`): a 14 s clip → READY, 3 renditions with correct content types, cache headers and CORS; delete removes everything.
  - The upload e2e's random bytes named `.mp4` → FAILED "Not a readable video file" with no retries.
  - Manual tests with a 14-minute iPhone portrait `.mov` (1.6 GB), recorded in the next bullet.
- **Manual crash tests** (1.6 GB iPhone `.mov`), all against the running stack:
  - **Hard crash:** SIGKILL at 25%, then restart → re-picked after 77 s (60 s lock at the time), leftover scratch wiped, READY, one output prefix, 1080x1920 poster.
  - **Clean stop:** SIGTERM at 10% → before the tini fix the stop took 30 s; after it, 1 s (exit 143). Row UPLOADED, job waiting, 0 attempts used, no output left in storage. The restarted worker re-picked it at once and it went READY in 9.5 min.

### Milestone 6: public playback
- **API** (`apps/backend/src/playback/`, public, no auth). Shapes are in `packages/contracts/src/playback.ts`.
  - `GET /videos`: the library. READY videos only, newest first, capped at 200 (a real library would paginate with a cursor). A READY row missing its output is skipped, so the list can't link to a dead player.
  - `GET /videos/:id/playback`: `status`, `progress`, `manifestUrl` (master), `posterUrl`, `durationSec`, `width`/`height` (after rotation), `renditions` (highest first, each with its own `playlistUrl`). Every playback field is null/empty until READY, so one response drives the processing, failed and ready states.
  - No admin-only fields go out: no file name/size, source key, or `failureReason` (it can hold ffmpeg/path details). The public page only says "couldn't be processed".
  - An unknown or malformed id is a 404 (not a 400): a broken shared link is "not found" to a viewer.
  - `Cache-Control`: READY answers get `public, max-age=0, s-maxage=60` (browsers revalidate with the ETag Express sends; a CDN may hold it 60 s, the same window as the playlists). Anything else gets `no-store`, because the page polls it.
  - Assumption: a video is public as soon as it's READY. There's no draft/unlisted flag; private videos are W5.
  - `HLS_VARIANT_PLAYLIST` (`index.m3u8`) moved into contracts; the worker's ffmpeg args use it, so the API and worker agree on the path.
- **Engine detection** (`apps/frontend/src/player/playbackMode.ts`), decided once per page:
  1. `canPlayType('application/vnd.apple.mpegurl') !== ''` → **native**. Covers Safari, every iOS browser and in-app webview (all WebKit), Android Chrome, Samsung Internet. Preferred because it's the only option on older iPhones, keeps AirPlay and the system fullscreen player, and uses less battery than JavaScript demuxing.
  2. Else `(ManagedMediaSource ?? MediaSource).isTypeSupported('video/mp4; codecs="avc1.640028,mp4a.40.2"')` → **hls.js**. Firefox, older desktop Chrome/Edge. The check runs without loading hls.js, then `Hls.isSupported()` confirms after the import.
  3. Else → **unsupported** state, with the stream URL for VLC.
  - `?player=native|hlsjs` forces an engine (only if the browser can do it), for testing both paths in one browser.
  - **Finding:** current desktop Chrome returns `"maybe"`, so it takes the native path (Chrome has added built-in HLS). Both paths were verified in Chrome via the override.
- **hls.js** is imported dynamically, so native-HLS devices never download it. It uses the **light build** (`hls.js/light`, 372 KB vs 595 KB), which leaves out subtitles, alternate audio and DRM; we don't use those. Switch to the full build if WebVTT captions are added. Config:
  - `capLevelToPlayerSize` (counts device pixel ratio), so a phone-sized player never pulls 1080p.
  - `startLevel: -1`: start from the bandwidth estimate (a low rung), then climb. Fast first frame.
  - `maxBufferLength 30` / `maxMaxBufferLength 60` ahead, `backBufferLength 30` behind. The default keeps everything played, which over a 10 h set would grow to gigabytes of memory.
  - `startPosition` = the resume point, so hls.js loads from there instead of from 0.
- **Quality selector.**
  - hls.js: `hls.currentLevel` (switches now, flushing the buffer; `nextLevel` would wait a segment), matched to our renditions by resolution; Auto = `-1`.
  - Native players have no rendition API, so a manual pick plays that rendition's own media playlist (`playlistUrl`) from the same position; Auto goes back to the master. `play()` is called inside the click handler, so iOS still treats it as user-initiated.
  - "Auto (720p)" shows what's playing from `videoWidth/videoHeight` (updated on `resize`), which works for both engines. Names follow the short side, so portrait 720x1280 is "720p".
- **Errors.** Pure decision functions in `playbackErrors.ts` (unit-tested).
  - hls.js already retries and switches down by itself; it only reports `fatal` once those run out. Fatal network → "Couldn't load the video" with **Try again**. Fatal media → `recoverMediaError()` up to 2 times (the budget resets after a clean fragment), then fail. Incompatible codecs → unsupported.
  - Native: MediaError 2 → network; 3 and 4 → a neutral "Playback stopped because of an error" (Chrome reports a failed segment fetch as 4, too), or network when offline; 1 (aborted) ignored.
  - Try again re-attaches the source at the last position.
  - Offline: a chip says playback continues on reconnect. On the browser's `online` event a network-failed player retries by itself. **Bug found and fixed in testing:** the first version retried on *any* network error while online, which looped silently against a blocked CDN; now only the offline→online event auto-retries.
- **Controls** (custom, because native controls differ per browser and can't host a quality menu).
  - The region is focusable (`role="region"`, `aria-roledescription="video player"`). YouTube's keys: Space/K, ←/→ 5 s, J/L 10 s, ↑/↓ volume, M, F, 0–9, Home/End. Keys that a focused control owns (Space on a button, arrows on a slider) are left to it. `aria-keyshortcuts` on the buttons, plus a "Keyboard shortcuts" list on the page.
  - Seek bar: a native `<input type=range>` (free keyboard and screen-reader support) with `aria-valuetext` "7:42:10 of 10:00:00". Arrows step 5 s, PageUp/Down 60 s (the browser default of 1% is 6 minutes on a 10 h video). Dragging only moves the thumb and shows a time bubble; it seeks once on release, so dragging across 10 h doesn't fire hundreds of segment requests. Clicks and screen-reader changes seek at once. Played and buffered ranges are painted on the one track with two CSS variables.
  - Quality menu: WAI-ARIA menu button with `menuitemradio` items. Opening focuses the checked item; arrows/Home/End move; Enter/Space pick; Esc closes and returns focus.
  - An `aria-live` region announces shortcut actions ("Forward 10 seconds", "Quality 480p", "Muted").
  - Controls auto-hide after 3 s of playback but stay visible while paused, while a menu is open, while dragging, on error, and while keyboard focus is inside. They stay in the accessibility tree when hidden.
  - Mouse click on the picture plays/pauses; a tap toggles the controls (the phone convention); double-click toggles fullscreen.
  - Optional controls drop out by the **player's** width (CSS container queries), not the screen's, because a portrait video on a laptop is a narrow player on a wide screen. The full set needs about 610 px with a 10 h timestamp. Volume slider from 42rem, ±10 s and PiP from 36rem, the quality label from 28rem, and "/ total" from 24rem. Play, mute, time, quality and fullscreen always fit. No volume slider on coarse pointers either (iOS ignores page-set volume). PiP only where `document.pictureInPictureEnabled`.
  - Portrait players are at least 20rem wide (a portrait video on a phone held sideways would otherwise be 165 px).
- **Mobile and webviews.**
  - `playsinline` plus the old `webkit-playsinline` (older iOS webviews, Facebook/Instagram), `x-webkit-airplay="allow"`, `preload="metadata"`, no autoplay.
  - Fullscreen (`player/fullscreen.ts`): the standard API (or `webkitRequestFullscreen`) on our container, so our controls stay. On iPhone, where only a `<video>` can go fullscreen, `webkitEnterFullscreen()` and iOS's own player, which handles rotation. On Android a landscape video locks the screen to landscape while fullscreen; refusals are ignored.
  - Media Session metadata (title, poster) for lock-screen controls.
  - The player box takes its aspect ratio from the API's width/height before anything loads (no layout jump), and portrait videos are sized to fit 75% of the viewport height.
- **Resume watching** (`player/watchProgress.ts`, unit-tested): one localStorage entry holding the 50 most recently watched videos.
  - Saved every 5 s, and on pause, seek, `pagehide` and page hidden (mobile may never fire unload), but only after real playback, so a page that sat at 0:00 can't overwrite a saved spot.
  - Under 10 s isn't saved. Within 30 s of the end counts as finished and is cleared, as is `ended`.
  - Every storage access is guarded: private mode and some webviews throw.
  - A "Resumed at 1:02:03 · Start over" chip shows on resume. The library shows a "Continue watching" bar.
- **Fast seek for long sets:** "Jump to time" accepts `7:42:10`, `42:10`, `90`, `7h42m10s` (`parseTimecode`, unit-tested), and `?t=` links take the same formats. A `?t=` link wins over the saved position. Seeking fetches only the segment at that time: verified that a jump to 4:00 requested `seg_00040`/`seg_00041` and nothing between.
- **Graceful states** on the watch page: loading skeleton; not found (unknown, malformed or deleted id); uploading/queued/processing with live % (polls every 5 s; viewers have no SSE, which is admin-only), turning into the player by itself; failed; unsupported browser; API unreachable with Try again. In the player: buffering spinner, fatal error with Try again, offline chip.
- **Bundle:** `AdminPage` and `LoginPage` are lazy chunks. Framer Motion moved into the admin page (the shared `ProgressBar` now uses a CSS transition). The session check (`/auth/me`) only runs when an admin screen calls `useAuth`, so public viewers don't send a request that 401s. Main chunk 522 → 410 KB (125 KB gzipped); hls.js is a separate chunk.
  - The auth and upload providers stay above the routes, so an upload keeps running while the admin opens the public pages (READY rows in the admin list now have a **Watch** link).

### Milestone 7: verification (in progress)
- **Extrapolating to 10 GB / 10 h from what was measured** (1 GiB upload in M4, 14-min iPhone `.mov` in M5, playback in M6). Only two things grow with size: **part/segment count** and **wall time**. Everything else is per part or per segment. Measured numbers are marked *measured*; the rest is arithmetic to confirm with the real files.
- **Upload (measured: 1 GiB, 64 parts, resumed after reload).**
  - 10 GB = 597 parts: 6 sign batches instead of 1, and still one ListParts page (S3 pages at 1,000; paging is implemented but no real upload under ~16 GB reaches it).
  - Work lost on a drop is at most 4 in-flight parts = 64 MiB, whatever the file size.
  - Bytes go browser → storage, so the API only sees small JSON calls whatever the size. Memory wasn't measured in M4; record `docker stats backend` and the browser heap during the M7 runs.
  - Wall time for 10 GB: 67 min at 20 Mbit/s, 2.2 h at 10, 4.4 h at 5. Two timeouts only show up in long uploads:
    - Part URLs (1 h TTL) re-sign 5 min before expiry, so any upload over ~55 min re-signs. Unit-tested, never hit in a browser (1 GiB on localhost takes minutes). Test with `UPLOAD_URL_TTL_SECONDS=60` and Chrome throttling.
    - **Open finding:** the 8 h session expires mid-upload below ~2.8 Mbit/s (10 GB × 8 / 8 h). What the engine does on a 401 from sign/status is unchecked. Test with a short `JWT_TTL_SECONDS`.
- **Processing (measured: 1080x1920, 14.1 min, 1.6 GB → 9.5 min encode, ~1.5x realtime, 650 MiB RSS, 920 MiB output = 9.1 Mbit/s summed, 428 objects).**
  - 10 h at a 1080p ladder: ~6.8 h encode, ~41 GB output, 18,005 objects (6,000 segments × 3 + 4 playlists + poster).
  - 10 h at a 720p ladder: estimated at 3–3.5 h from pixel count alone. **Measured on a real 10 h 720p video: ~75 min projected** (see the runs below). Content matters more than the pixel estimate suggested.
  - Expected worker memory to stay flat. **Measured: it isn't.** ffmpeg RSS grows ~4 MiB per progress point (~730 MiB projected at the end of the encode); Node stays flat. Likely the HLS muxer's in-memory segment lists; not confirmed.
  - Lock and heartbeat: the 9.5 min run had no lock errors and a max progress gap of 12 s. A 7 h run is ~400 lock renewals of the same kind; not proven over hours.
  - A crash restarts the encode from 0 (known limitation, W2).
- **Disk (finding from the extrapolation).**
  - The worker's pre-flight check needs source + caps × duration × 1.1 + 1 GiB. For a 10 h / 10 GB 1080p source that's ~60 GB of free scratch; for the 11 GB 720p synthetic file, ~40 GB.
  - Peak disk for a 10 h 1080p video is ~100 GB: source in MinIO + scratch copy + output on scratch + output in MinIO.
  - **On Docker Desktop the check can't see the real limit.** Inside a container `statfs` reports the VM's sparse 1 TB disk (905 GB "free") while the Mac had 62 GB free. On a Linux host or EC2 it sees the real volume. Before the 10 h runs, free space (`docker system df`: ~36 GB reclaimable, 21 GB of it build cache). README: state the disk needed.
  - Production fix (W2/W7): upload segments as they're produced and delete them locally, so scratch only needs the source.
- **Playback (measured on the 14-min video).**
  - Seeking fetches only the segment at the target (4:00 → `seg_00040`/`seg_00041`), so seek cost doesn't depend on duration. Prediction for 07:42:10 (27,730 s / 6 s): `seg_04621`.
  - Variant playlists grow to 6,000 entries, ~180 KB each, fetched once at start: about 0.5 s on a 3 Mbit/s phone connection. Playlists compress well if the CDN gzips them.
  - hls.js buffers are capped (30 s back, ≤60 s ahead), so player memory doesn't grow with duration.
  - The control bar already fits a 10 h timestamp (M6). On a ~600 px seek bar a pixel is ~60 s; keyboard steps and "Jump to time" give precise seeks.
- **First real 10 h run** (`10-hours-Earth-from-Space…_720p.mp4`: 10:03:46, 1280x720 H.264 25 fps, 1.97 GB):
  - Upload: 1.8 GiB on localhost in under 15 s.
  - Encode (720p ladder): 5 → 20% in 13.7 min, steady at ~4.6 min per 5 points, so about 78 min projected for the whole encode (~7.7x realtime). That's far faster than the 3–3.5 h estimate: the content is slow-moving, the source is 25 fps and the ladder is 720p.
  - Worker memory 800 → 834 → 857 MiB at 10/15/20%. It may be page cache from the segment writes; check against ffmpeg's own RSS on the next run.
  - Stopped by the author at 20% with `docker compose stop worker`: stopped in <1 s, row UPLOADED with 0 attempts used, `run0` back in `wait`, no partial output under `public/`, source kept. A restart re-encodes from 0 (no mid-encode resume; W2).
- **Second run, same upload** (`docker compose start worker`): re-picked at once, 0 attempts used. 5 → 30% in 22 min (~0.88 min per point), so about 75 min projected for the whole encode. ffmpeg RSS 381 → 402 → 414 → 448 → 463 → 474 MiB at 5–30% (~4 MiB per point, ~730 MiB projected at the end of the encode); Node flat at ~135 MiB; container 676 → 798 MiB. No lock, stall or error lines in the worker log. Stopped again at 30% by the author; row back to UPLOADED, 0 attempts used. **Not run to READY yet**, so the 10 h playback checks (07:42:10 seek, resume) are still open.

  - One 10 GB upload (rubric: "10 GB upload works").
  - The 10 h video reaching READY, then the 07:42:10 seek and resume on it.
  - Output size and object-upload time for 10 h.
